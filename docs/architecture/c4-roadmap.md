# C4 Roadmap — Pig Console

Дорожная карта описания целевой архитектуры проекта **Pi Games (Pig) Console**
в рамках парадигмы «architecture as a code» на основе LikeC4 и C4 Model.

## Статус

Выполнено описание **слоя Context (уровень 1)** и **слоя Container (уровень 2)**:

- `docs/architecture/likec4.config.json` — конфиг проекта `pig-console`
- `docs/architecture/spec.c4` — виды элементов: `person`, `system`, `container`, `external-system`
- `docs/architecture/context.c4` — модель слоя Context
- `docs/architecture/containers.c4` — модель слоя Container

`npx likec4 validate --json --no-layout --file spec.c4 --file context.c4 --file containers.c4 --file views.c4 docs/architecture`

## Зафиксированные решения (Context)

- **Граница системы**: описываемая система — только UI-оболочка `pig-console-shell`; железо, ОС и внешние приложения находятся вне границы.
- **Внешние приложения**: Игры, Браузер, Терминал — отдельные внешние системы, которыми оболочка управляет по протоколу Wayland IVI shell.
- **Игровой репозиторий**: внешний источник игровых пакетов. Поиск, установка, обновление, удаление игр и управление их настройками выполняются через собственный менеджер игровых пакетов оболочки.
- **PackageKit**: системный менеджер пакетов дистрибутива Linux (D-Bus) — источник информации о системных обновлениях и способ их запуска.
- **Композитор**: пишем сами, но поверх внешней библиотеки, реализующей практически все аспекты Wayland-композитора (например, smithay). Код проекта сосредоточен на логике UI-оболочки.
- **Пользователи**: Игрок (только геймпад), Администратор (клавиатура, работа через терминал).
- **Название**: *Pig* — сокращение от *Pi Games* с игрой слов (похоже на англ. *pig*, «свинья»); маскот — свинка, играющая в игры.

## Container-слой (выполнено)

**Compositor Core — свёрнут в UI Shell.** Оболочка и композитор живут в одном процессе (единый бинарник поверх внешней библиотеки, например, smithay), поэтому по канону C4 это один контейнер, а не два. Compositor Core детализируется как компонент на слое Components — см. `c4-components-roadmap.md`.

**Обоснование состава контейнеров (критерий развёртывания).** Остальные три контейнера имеют высокие шансы быть отдельными процессами или хранилищем, что оправдывает их контейнерный уровень:

- **Game Launcher** — отдельный процесс: монтирование squashfs требует повышения привилегий, поэтому этот функционал изолируется в независимый процесс с минимальным функционалом (SUID-бинарник).
- **Game Library** — в значительной части база данных на лёгкой СУБД (например, SQLite).
- **Package/Update Manager** — долгие операции скачивания и системные обновления через PackageKit тяготеют к отдельной службе.

Решение представлено на уровне Containers **на текущий момент**; в будущем оно может быть пересмотрено (например, при переходе к слою Components).

Итоговый состав контейнеров:

- **UI Shell** — основной интерфейс пользователя; реализует практически все аспекты Wayland-композитора поверх внешней библиотеки; управление layout'ом запускаемых приложений (игра, браузер, терминал); обработка навигации с геймпада; запуск браузера и терминала.
- **Game Launcher** — запуск установленной игры: монтирование squash-fs образа, чтение запрошенных прав из манифеста, учёт пользовательских разрешений, запуск игрового приложения; предоставляет данные манифеста другим подсистемам. Функционал монтирования вынесен в отдельный SUID-процесс.
- **Package/Update Manager** — получение каталога и скачивание игр из репозитория, детектирование обновлений установленных игр, системные обновления через PackageKit; уведомляет UI Shell об обновлениях и получает от неё команды на их запуск.
- **Game Library** — владелец установленных игр и их ресурсов (сохранения, скриншоты); независимое удаление игры и её ресурсов; интерфейс хранения настроек игр (например, флаг «любимая» для порядка в списке). В значительной части — база данных на лёгкой СУБД (например, SQLite).

Свёрнутые элементы прежних гипотез:

- **Compositor Core** (контейнер) — свёрнут в **UI Shell**, перенесён на Components-слой.
- **Input Manager** — свернут в **UI Shell** (навигация с геймпада — часть интерфейса); клавиатурный/указательный ввод остаётся зоной ответственности компонента Compositor Core (seat).
- **Session Manager** — не выделяется; браузер и терминал запускает напрямую **UI Shell**. **Game Launcher** отвечает только за запуск игр (squashfs, манифест, права).

Сценарии «жизненного цикла» игр (поиск, установка, просмотр списка, настройки, удаление) легли на связку **UI Shell → Game Library + Package/Update Manager**, с проверкой обновлений через **Game Library**.

## Следующие задачи

### Задача 1. Ключевые сценарии (dynamic views)

Описать основные потоки взаимодействия, используя построенные модель и диаграммы:

- загрузка консоли и вход в главное меню;
- запуск игры геймпадом и переход в полноэкранный режим;
- переключение между окнами (layout'ы оболочки);
- поиск и установка игры через репозиторий, просмотр библиотеки, настройки и удаление игры;
- сеанс администрирования через терминал (ввод с клавиатуры).

Каждый сценарий оформляется как `dynamic view` на базе элементов Context/Container. Это позволит проверить согласованность модели до перехода к Deployment.

### Задача 2. Deployment-слой (физическое развёртывание)

Описать фактическую топологию на Raspberry Pi:

1. Ввести виды `deploymentNode`: устройство (Raspberry Pi), периферия (дисплей/HDMI, геймпад, клавиатура).
2. В блоке `deployment` привязать логические элементы через `instanceOf`: `pig-console-shell` → Raspberry Pi.
3. Создать deployment-view и провалидировать проект.

## Дальнейшее (вне ближайших задач)

- **Component-слой** — декомпозиция контейнеров до компонентов; стартует с UI Shell (в т.ч. Compositor Core). Текущее видение — в `c4-components-roadmap.md`.
- **ADR** — зафиксировать ключевые решения в виде записей Architecture Decision Records: выбор библиотеки композитора, привязка к протоколу IVI shell, gamepad-first UX, формат игровых пакетов (squashfs + манифест прав).
- **Стандарт описания** — конвенции по стилям, тегам и структуре файлов при росте модели.
