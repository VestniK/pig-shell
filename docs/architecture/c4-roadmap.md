# C4 Roadmap — Pig Console

Дорожная карта описания целевой архитектуры проекта **Pi Games (Pig) Console**
в рамках парадигмы «architecture as a code» на основе LikeC4 и C4 Model.

## Статус

Выполнено описание **слоя Context (уровень 1)** и **слоя Container (уровень 2)**:

- `docs/architecture/likec4.config.json` — конфиг проекта `pig-console`
- `docs/architecture/spec.c4` — виды элементов: `person`, `system`, `container`, `external-system`
- `docs/architecture/context.c4` — модель слоя Context
- `docs/architecture/containers.c4` — модель слоя Container
- `docs/architecture/views.c4` — диаграммы Context и Containers
- `docs/architecture/out/` — экспортированные PNG

Валидация всех файлов проходит (запуск из каталога `docs/architecture`):
`npx likec4@1.59.4 validate --json --no-layout --file spec.c4 --file context.c4 --file containers.c4 --file views.c4 .`

Версия CLI выбрана в соответствии с языковым сервером IDE: старые версии
(например, 1.53.0) не принимают `<->` внутри блоков контейнеров и `description`
в видах связей.

## Зафиксированные решения (Context)

- **Граница системы**: описываемая система — только UI-оболочка `pig-console-shell`; железо, ОС и внешние приложения находятся вне границы.
- **Внешние приложения**: Игры, Браузер, Терминал — отдельные внешние системы, которыми оболочка управляет по протоколу Wayland IVI shell.
- **Игровой репозиторий**: внешний источник игровых пакетов. Поиск, установка, обновление, удаление игр и управление их настройками выполняются через собственный менеджер игровых пакетов оболочки.
- **PackageKit**: системный менеджер пакетов дистрибутива Linux (D-Bus) — источник информации о системных обновлениях и способ их запуска.
- **Самообновление консоли**: компоненты Pig Shell, Pig Library и Pig Pkg распространяются в виде системных пакетов дистрибутива и обновляются через PackageKit — отдельный канал обновлений не требуется.
- **Аудио**: звуковой сервер — PipeWire из нижележащей ОС. Является контрактом, на который могут рассчитывать игры: игры выводят звук напрямую через PipeWire. Взаимодействие pig со звуком — часть Pig Shell; звуковые эффекты UI отложены на последующие итерации.
- **Сеть**: системный NetworkManager из дистрибутива. В первой итерации настройка сети выполняется администратором через терминал (nmcli/nmtui); UI-фронтенд к NetworkManager в Pig Shell — отложено.
- **Питание**: выключение и перезагрузка устройства через systemd-logind (D-Bus) — требуются с самого старта, выполняются Pig Shell.
- **Ввод для браузера**: в первой итерации браузер используется с клавиатурой и мышью; управление браузером с геймпада — отложено. Экранная клавиатура для ввода текста с геймпада — компонент Pig Shell на слое Components, отложена (см. `c4-components-roadmap.md`).
- **Композитор**: пишем сами, но поверх внешней библиотеки, реализующей практически все аспекты Wayland-композитора (например, smithay). Код проекта сосредоточен на логике UI-оболочки.
- **Пользователи**: Игрок (только геймпад), Администратор (клавиатура, работа через терминал).
- **Название**: *Pig* — сокращение от *Pi Games* с игрой слов (похоже на англ. *pig*, «свинья»); маскот — свинка, играющая в игры.

## Container-слой (выполнено)

Внутри системы **Pig Console Shell** выделены три отдельных приложения-контейнера, разделённых по критерию отдельного процесса/развёртывания. Состав пересмотрен после обнаружения неоднозначностей в прежней схеме из четырёх контейнеров (Game Library, Package/Update Manager, Game Launcher, UI Shell), где пересекались зоны ответственности за поток обновлений.

Итоговый состав контейнеров:

- **Pig Shell** — отдельное приложение-композитор и основной GUI системы. Реализует практически все аспекты Wayland-композитора поверх внешней библиотеки (например, smithay); управляет layout'ом окон (игра, браузер, терминал), обрабатывает навигацию с геймпада, запускает браузер и терминал. Сама по себе не содержит сложной логики: всё управление библиотекой игр, обновлениями и запуском игр делегирует приложению **Pig Library**.
- **Pig Library** — D-Bus сервис в пользовательской systemd-сессии. Инкапсулирует всю сложную логику: владеет установленными играми и их ресурсами (сохранения, скриншоты), взаимодействует с внешним репозиторием игр, детектирует и выполняет обновления (игр — путём управления составом библиотеки; системы — через PackageKit), запускает игры, делегируя низкоуровневую работу утилите **Pig Pkg**. Является единственным провайдером данных и исполнителем действий для Pig Shell.
- **Pig Pkg** — низкоуровневая SUID-утилита (CLI), работающая с отдельным игровым пакетом. Монтирует squash-fs образ, читает разрешения из манифеста, учитывает пользовательские разрешения, настраивает изоляцию (sandbox), понижает привилегии и делает `exec` приложения игры. Не содержит бизнес-логики библиотеки или обновлений.

Принцип построения слоя:

- **Единый канал сложной логики.** Pig Shell не общается с репозиторием, PackageKit или Pig Pkg напрямую. Всё — через Pig Library, что убирает пересечение зон ответственности.
- **Поток обновлений.** Pig Shell через Pig Library получает информацию о доступных обновлениях игр и системы; запуск обновлений инициируется пользователем через Pig Shell и делегируется в Pig Library.
- **Поток запуска игры.** Игрок → Pig Shell → Pig Library → Pig Pkg → игры → (ivi-поверхность) → Pig Shell.
- **Внутренние нюансы реализации** — хранение персистентных данных в лёгкой СУБД, дробление библиотеки/менеджера пакетов/детектора обновлений — переносятся на Components-слой, поскольку используются исключительно внутри Pig Library. См. `c4-components-roadmap.md`.

Свёрнутые элементы прежней гипотезы:

- **UI Shell** (контейнер) — переименован в **Pig Shell**, состав зон ответственности сужен: композитор + GUI + layout, делегирование; вся бизнес-логика ушла в **Pig Library**.
- **Game Library + Package/Update Manager** (два контейнера) — объединены в **Pig Library**: прежние сущности стали её внутренними компонентами на Components-слое.
- **Game Launcher** (контейнер) — переименован в **Pig Pkg**, роль сужена до SUID-утилиты для работы с отдельным пакетом, без бизнес-логики.
- **Compositor Core** и **Input Manager** — перенесены на Components-слой внутрь **Pig Shell** (см. `c4-components-roadmap.md`).
- **Session Manager** — не выделяется; браузер и терминал запускает напрямую **Pig Shell**.

## Конвенция отложенных блоков (#deferred)

Блоки, сознательно откладываемые на последующие итерации разработки, помечаются в модели:

- **Элементы** — тегом `#deferred` (определён в `spec.c4`); в `views.c4` приглушаются правилом `style element.tag = #deferred { color muted; opacity 40%; border dashed }`.
- **Связи** — видом связи `deferred` (`-[deferred]->`); приглушённый пунктирный стиль задан по умолчанию спецификацией вида в `spec.c4`, поскольку правила `style` в views не распространяются на связи.

Пометка означает: «в целевой архитектуре присутствует, но не входит в первую итерацию реализации».

## Следующие задачи

### Задача 1. Ключевые сценарии (dynamic views)

Описать основные потоки взаимодействия, используя построенные модель и диаграммы:

- загрузка консоли и вход в главное меню;
- запуск игры геймпадом и переход в полноэкранный режим;
- переключение между окнами (layout'ы оболочки);
- поиск и установка игры через репозиторий, просмотр библиотеки, настройки и удаление игры;
- сеанс администрирования через терминал (ввод с клавиатуры).

Каждый сценарий оформляется как `dynamic view` на базе элементов Context/Container. Это позволит проверить согласованность модели до перехода к Deployment.

### Задача 2. Deployment-слой (физическое развёртывание)

Описать фактическую топологию на Raspberry Pi:

1. Ввести виды `deploymentNode`: устройство (Raspberry Pi), периферия (дисплей/HDMI, геймпад, клавиатура).
2. В блоке `deployment` привязать логические элементы через `instanceOf`: `pig-console-shell` → Raspberry Pi.
3. Создать deployment-view и провалидировать проект.

## Дальнейшее (вне ближайших задач)

- **Component-слой** — декомпозиция контейнеров до компонентов; стартует с **Pig Shell** (в т.ч. Compositor Core, Layout Manager, Gamepad Input) и **Pig Library** (в т.ч. хранилище игр, менеджер пакетов, детектор обновлений). Текущее видение — в `c4-components-roadmap.md`.
- **ADR** — зафиксировать ключевые решения в виде записей Architecture Decision Records: выбор библиотеки композитора, привязка к протоколу IVI shell, gamepad-first UX, формат игровых пакетов (squashfs + манифест прав).
- **Стандарт описания** — конвенции по стилям, тегам и структуре файлов при росте модели.
