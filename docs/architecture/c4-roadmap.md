# C4 Roadmap — Pig Console

Дорожная карта описания целевой архитектуры проекта **Pi Games (Pig) Console**
в рамках парадигмы «architecture as a code» на основе LikeC4 и C4 Model.

## Статус

Выполнено описание **слоя Context (уровень 1)**:

- `docs/architecture/likec4.config.json` — конфиг проекта `pig-console`
- `docs/architecture/spec.c4` — виды элементов: `person`, `system`, `external-system`
- `docs/architecture/context.c4` — модель слоя Context
- `docs/architecture/views.c4` — контекстная диаграмма
- `docs/architecture/out/context.png` — экспортированная диаграмма

Валидация всех файлов проходит: `npx likec4 validate --json --no-layout --file spec.c4 --file context.c4 --file views.c4 docs/architecture`

## Зафиксированные решения (Context)

- **Граница системы**: описываемая система — только UI-оболочка `pig-console-shell`; железо, ОС и внешние приложения находятся вне границы.
- **Внешние приложения**: Игры, Браузер, Терминал — отдельные внешние системы, которыми оболочка управляет по протоколу Wayland IVI shell.
- **Игровой репозиторий**: внешний источник игровых пакетов. Поиск, установка, обновление, удаление игр и управление их настройками выполняются через собственный менеджер игровых пакетов оболочки.
- **Композитор**: пишем сами, но поверх внешней библиотеки, реализующей практически все аспекты Wayland-композитора (например, smithay). Код проекта сосредоточен на логике UI-оболочки.
- **Пользователи**: Игрок (только геймпад), Администратор (клавиатура, работа через терминал).
- **Название**: *Pig* — сокращение от *Pi Games* с игрой слов (похоже на англ. *pig*, «свинья»); маскот — свинка, играющая в игры.

## Замечание про Compositor Core

`compositor-core` сейчас представлен на слое Context как **внешняя система**. По канону C4 сторонние библиотеки обычно появляются не на Context, а на **слое Container** — как технология/зависимость одного из контейнеров.

Текущая трактовка допустима, пока мы не построили Container-слой, и помогает подчеркнуть значимость этой внешней зависимости. При переходе к **Задаче 1** решаем:

- переместить `compositor-core` внутрь контейнера «Compositor Core» как его технологию (вариант по умолчанию), либо
- оставить как внешний элемент, если решим, что библиотека архитектурно значима на уровне системы.

Во втором случае убеждаемся, что это осознанное отклонение от канона, и фиксируем причину в ADR.

## Заметки к Container-слою: сценарии управления играми

Сценарии «жизненного цикла» игр (поиск, установка, просмотр списка установленных, настройки, удаление) уже отражены на Context через внешний `game-repository`. На **Container-слое** под них потребуется выделить как минимум следующие компоненты:

- **Game Package Manager** — менеджер игровых пакетов: поиск и получение метаданных из репозитория, скачивание, установка, обновление и удаление игр; клиент HTTP API `game-repository`.
- **Game Library** — локальное хранилище установленных игр и их метаданных: список игр, версии, статус установки, пользовательские настройки игр.
- **UI игрового каталога/библиотеки** — экраны оболочки: поиск, список установленных игр, страница игры (запуск, настройки, удаление). Вероятно, часть **Launcher UI**.

Эти компоненты уточняются в Задаче 1 по мере декомпозиции системы.

## Следующие задачи

### Задача 1. Container-слой системы Pig Console Shell

Разбить `pig-console-shell` на контейнеры (гипотеза для старта):

- **Launcher UI** — основной интерфейс оболочки: меню приложений, каталог и библиотека игр, навигация по геймпаду
- **Shell / Window Manager** — реализация раскладки окон на основе IVI shell, фокус и зонирование
- **Input Manager** — приём ввода с gamepad/клавиатуры, маппинг в действия навигации
- **Session Manager** — запуск внешних приложений (игры/браузер/терминал) и управление их жизненным циклом
- **Game Package Manager** — менеджер игровых пакетов (см. заметки выше)
- **Game Library** — локальное хранилище установленных игр и их настроек
- **Compositor Core** — контейнер-обёртка над внешней библиотекой композитора

Шаги:

1. Уточнить состав контейнеров и связи между ними (в том числе с внешними приложениями через IVI shell).
2. Перенести `compositor-core` с Context на Container-уровень согласно замечанию выше.
3. Добавить `container` в `spec.c4`.
4. Создать container-view и провалидировать проект.

### Задача 2. Ключевые сценарии (dynamic views)

Описать основные потоки взаимодействия, используя уже построенные модель и диаграммы:

- загрузка консоли и вход в главное меню;
- запуск игры геймпадом и переход в полноэкранный режим;
- переключение между окнами (layout'ы оболочки);
- поиск и установка игры через репозиторий, просмотр библиотеки, настройки и удаление игры;
- сеанс администрирования через терминал (ввод с клавиатуры).

Каждый сценарий оформляется как `dynamic view` на базе элементов Context/Container. Это позволит проверить согласованность модели до перехода к Deployment.

### Задача 3. Deployment-слой (физическое развёртывание)

Описать фактическую топологию на Raspberry Pi:

1. Ввести виды `deploymentNode`: устройство (Raspberry Pi), периферия (дисплей/HDMI, геймпад, клавиатура).
2. В блоке `deployment` привязать логические элементы через `instanceOf`: `pig-console-shell` → Raspberry Pi.
3. Создать deployment-view и провалидировать проект.

## Дальнейшее (вне ближайших трёх задач)

- **Component-слой** — декомпозиция контейнеров до компонентов, только если потребуется для принятия решений по коду.
- **ADR** — зафиксировать ключевые решения в виде записей Architecture Decision Records: выбор библиотеки композитора, привязка к протоколу IVI shell, gamepad-first UX, отклонения от канона C4 (если появятся).
- **Стандарт описания** — конвенции по стилям, тегам и структуре файлов при росте модели.
